# E7 stable-paused rendering prototype

Local development only, based on main9cf2f5e. Existing version/revision remain baseline identifiers, not a published new version. No rendering or power improvement has yet been observed on this candidate.

Only the renderer submission is conditional. requestAnimationFrame, realDt/previous, Game.step, input, hover, camera, visual sync, DOM overlays, choice timing and CSS animation continue through the original loop. Non-paused states always submit. Stable paused needs its first frame, explicit dirty/invalidation, status change or camera/viewport/DPR signature change to submit another WebGL render. The gate consumes a dirty request only when choosing to draw; main preserves dirty flags before sync clears them.

Invalidations include original renderDirty (reset, atlas-ready, restored context, presentation changes), resize and quality changes, DPR polling, focus/blur/pageshow, visibility/fullscreen, input/change/click/keyboard/focus transitions, overlay/dialog mutations, reduced-motion change, context loss/restoration and explicit QA renderOnce/preview. Camera world matrices are updated before computing the render signature. DOM/CSS animations remain browser-composited and are not disabled by this gate. No timer/RAF cancellation or global idle scheduler is introduced.

## Required validation before accepting a product change

QA1 owns actual browser execution after PM arranges a slot; QA2 owns original-image review per e7-visual-checklist-t24.md. DEV does not accept its own visuals. First use the existing unchanged e7-measure.mjs on separate clean baseline9cf and fixed candidate: same hardware, actual renderer (not requested backend), Node/browser versions, 1280x720/DPR1/balanced/map0, low-load and dense fixed scenes, 3 rounds each, running→paused→resumed. Retain prior5s windows to permit method-consistent comparison; a later longer/alternating sample protocol is a separate bounded decision, not an automatic retry. Baseline and candidate must each have their own evidence and exact ownership cleanup.

Acceptance to investigate further: stable-paused render submissions should fall to zero after its redraws settle in these fixed scenes; running/resumed continue submitting, scene/camera/time/status invariants and screenshots remain correct. No invented percentage improvement is required to pass functionality, and any new FAIL stops the batch. If benefit is absent or behavior regresses, retain FAIL and reassess this prototype rather than widening scope automatically.

Targeted functional evidence must cover first pause, stable pause, each setting preview, dialog open/close, resize and DPR-only changes, real hide/show, focus, atlas-ready and context restoration, renderOnce, rapid resume/re-entry. For each record source SHA/manifest, transition times/status/game time/camera, renderer-call delta, errors, original PNG path and cleanup. CSS/DOM animations and settings remain usable; a screenshot alone cannot establish RAF, game-clock or render-call behavior. Running/pickup/upgrade/ready/ended paths must retain existing validation. Chrome and applicable Firefox work remain separate; Safari and mobile are not implied.

No wattage, battery-life, whole-CPU/GPU-time or stability claim follows from reduced JS renderer calls. Hardware power equipment is not currently confirmed. This stage can establish less submitted work and correct behavior; real energy testing needs a separately confirmed method/device. Existing fixed-order E7 baseline and old18 images remain historical evidence, not candidate validation. E7 remains open.

## Cost / risk

Focused pure and DOM tests plus export validation are local preparation. Later actual six-round baseline/candidate measurement, full Chrome and targeted transitions should be a single sequenced GPU handoff, bounded by the unchanged runner's limits; allow approximately30–45 minutes plus QA2 inspection, subject to PM scheduling. Extended five30-second-condition alternating tests from the prior design are optional follow-up only after this first functional candidate is sound, not part of this offline delivery. Risks still needing actual browser evidence: driver/compositor persistence when no WebGL frame occurs, context recovery, async texture presentation, per-browser DPI/focus events, and mutation-driven over-invalidation. Stable render reduction may leave significant RAF/JS/DOM work unchanged; this prototype is intentionally limited to render submission.
